## What I Was Trying to Do

I had already started a Node.js project locally.

```bash
mkdir my-project && cd my-project
git init -b main
echo "console.log('hello')" > src/index.js
git add src
git commit -m "Initial local commit"
```

Only afterward did I realize I had also created a same-named repository on GitHub with "Add a README file" checked. I registered the remote locally, fetched it, and tried to merge the two `main` branches.

```bash
git remote add origin git@github.com:example-org/my-project.git
git fetch origin
git branch -a
```

```text
* main
  remotes/origin/main
```

```bash
git merge origin/main
```

```text
fatal: refusing to merge unrelated histories
```

`git pull origin main` failed the same way. Both the local `main` and the remote `main` were each their own very first commit, with no common ancestor between them, so Git couldn't be sure this was actually a continuation of the same project — and refused to merge.

## Environment

- OS: Ubuntu 24.04 LTS
- Git: 2.43.0
- Situation: a locally `git init`-ed project connected via `git remote add` to a GitHub repository that had already been created with a README

## What I Tried

At first I assumed re-running `git pull origin main` would just work eventually, but it kept failing with the same error.

```bash
git pull origin main
```

```text
fatal: refusing to merge unrelated histories
```

Next I checked whether the remote commit actually existed with `git log`.

```bash
git log --oneline --all --graph
```

```text
* 82e3a6b Initial local commit
* e128024 Initial commit from GitHub template
```

The `--graph` output makes it look like a single linear history, but that's only because it's sorted by date — there is no parent/child relationship (no common ancestor) between `82e3a6b` and `e128024` at all. That's when I realized this wasn't an ordinary conflict; it was two repositories with genuinely independent origins being forced together.

## Root Cause

Since Git 2.9, `git merge` and `git pull` refuse by default to merge two histories that don't share a common ancestor commit. This is a safety guard against accidentally fetching and merging two completely unrelated projects.

In this case, both sides had their own independent first commit:

- The very first commit made locally with `git init` (`Initial local commit`)
- The first commit auto-generated by GitHub when the repository was created with "Add a README file" checked (`Initial commit from GitHub template`)

Both are "the first commit of that repository," so they can't share a parent by definition. A normal `fetch` + `merge` flow can't reconcile that — you have to explicitly state that you know the histories are unrelated and want to merge them anyway.

## How I Fixed It

### 1. Check the current state

```bash
git branch -a
```

```text
* main
  remotes/origin/main
```

Confirmed both the local `main` and `origin/main` existed and hadn't been merged yet.

### 2. Merge with `--allow-unrelated-histories`

```bash
git merge origin/main --allow-unrelated-histories -m "Merge remote-tracking branch 'origin/main' into main"
```

```text
Merge made by the 'ort' strategy.
 README.md | 1 +
 1 file changed, 1 insertion(+)
 create mode 100644 README.md
```

The merge completed without an error. In this case there were no filename collisions between the two sides, so no conflict markers appeared. If both sides had a file with the same name (e.g., both had a `README.md`), you'd need to resolve it manually just like any ordinary merge conflict.

### 3. Check the history after the merge

```bash
git log --oneline --graph --all
```

```text
*   5ce7cd2 Merge remote-tracking branch 'origin/main' into main
|\
| * e128024 Initial commit from GitHub template
* 82e3a6b Initial local commit
```

The two independent histories were correctly joined into one at merge commit `5ce7cd2`.

### 4. Push to the remote

```bash
git push -u origin main
```

```text
   e128024..5ce7cd2  main -> main
branch 'main' set up to track 'origin/main'.
```

## Verifying It Worked

```bash
ls -la
```

```text
README.md
src/
```

Both the local `src/index.js` and GitHub's `README.md` were present in the working directory. `git status` was clean, and the tracking relationship (`main` tracking `origin/main`) was correctly set up.

## Summary

- `fatal: refusing to merge unrelated histories` is a safety guard Git raises when you try to `merge` or `pull` two histories with no common ancestor commit — it isn't an ordinary merge conflict.
- The classic trigger is connecting a project you already ran `git init` on locally to a GitHub repository created with "Add a README file" checked; each side ends up with its own independent first commit.
- Only when you're certain both sides really are the same project, merge explicitly with `git merge origin/main --allow-unrelated-histories` (or `git pull origin main --allow-unrelated-histories`). If any filenames collide, you'll still need to resolve the conflict normally.

## FAQ

**Q: Does `--allow-unrelated-histories` work with `git pull` too?**
Yes. `git pull origin main --allow-unrelated-histories` runs `fetch` + `merge` in one command, and internally does the same thing as the `git merge --allow-unrelated-histories` shown above.

**Q: When is it risky to use this flag?**
If you accidentally `fetch` and merge a genuinely unrelated (different) repository, this flag will happily merge in files that have nothing to do with your project. Always check with `git log --oneline --all --graph` first to confirm both histories really are continuations of the same project before using it.

**Q: How can I avoid this situation entirely?**
When creating the repository on GitHub, leave "Add a README file" unchecked so it starts empty, then push your existing local project to it first. Since only one side will have any history at that point, this error can't occur in the first place.
